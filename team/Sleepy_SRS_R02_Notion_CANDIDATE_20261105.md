## 0. 이 문서를 읽는 방법

이 문서는 기업 과제의 요구사항을 개발·검증 가능한 수준으로 구체화한 **초안**이다. 본 문서에 적혔다는 이유만으로 팀 승인, 개발 완료 또는 기업 확인을 의미하지 않는다.

| 구분 | 의미 | 이 문서에서의 처리 |
|---|---|---|
| **[E] 기업 과제 요구** | 제공된 기업 과제 브리핑에서 확인된 요구 | 필수 구현/제출 기준으로 식별 |
| **[T] 팀 합의·사용자 확인** | 현재 대화에서 확인된 팀 결정 | 현행 설계 경계로 반영. 필요 시 팀 회의에서 재확인 |
| **[P] 설계 제안** | 개발을 위해 제안한 구체적 방식·기준 | 검토 전 확정으로 취급하지 않음 |
| **[O] 미결** | 기업·팀·환경 확인이 필요한 사항 | 추정으로 메우지 않음 |
| **[X] 범위 제외** | 기업 과제의 제외 범위 | MVP 필수로 승격하지 않음 |

**원문 확보 범위:** 기업 과제 요구의 기존 정리 기록과 이 대화에서 직접 확인된 팀 합의를 기준으로 작성했다. 실제 `7.FAQ.docx`의 21개 **답변 전문**, 실제 제품 모델 목록, 공식 상담 URL, 기업의 최종 승인본은 직접 대조하지 못했다. 기존 정리 문서도 정본 원문을 대체하지 않는다. 과제 브리핑 원문과 충돌하면 실제 브리핑 확인 및 수정이 필요하다.

## 1. 프로젝트 정의

### 1.1 목적 [E]

Sleepy의 제품 설명, 사용 안내, 구매 정보, FAQ 및 제공되는 문의 사례를 검색 가능한 지식으로 활용해, 고객이 자연어로 질문하면 관련 자료에 근거한 답변을 제공하는 **홈페이지 연동 가능 RAG 챗봇 MVP**를 개발한다. 자료에 근거가 없거나 개별 처리가 필요한 요청은 추측하지 않고 고객지원 채널을 안내한다.

### 1.2 사용자·이해관계자

| 사용자/관계자 | 핵심 목적 | 범위 |
|---|---|---|
| 고객 | 제품·사용법·주의·구매 정보 확인 | 고객 UI 필수 |
| 기업 고객지원 담당자 | 챗봇이 답할 수 없는 문의 수신 | 기존 문의 채널 연결, 상담 시스템 신설 제외 |
| 웹서비스 개발팀 | 기존 홈페이지에 챗봇 삽입 | 연동 형태와 기술 제약 협의 |
| 프로젝트 팀원 | 데이터, UI, API, RAG, 평가·배포 수행 | 담당 배분은 팀 합의 대상 |

### 1.3 현재 확정·미확정 경계

| 항목 | 상태 | 근거/주의 |
|---|---|---|

| 제품별 수동 분류 | **[O] 미확정·필수 아님** | 자동 매칭을 우선 검토. 제품 혼동 방지책 필요 |
| 기술 스택 Python/FastAPI/LangChain/GPT API | **[P] 현 논의 방향** | 구현·계약·배포 사실로 단정 금지 |

| 공식 FAQ 원본 21건 | **확인된 기존 관리 범위** | 고객 공개 승인 및 전체 답변 원문 별도 대조 |
| 통합 대표 FAQ 89건 | **기존 정리 결과** | 전체 89건이 공식 승인 답변이라는 뜻 아님 |

## 2. 범위·우선순위

### 2.1 기업 필수 MVP [E]

1. 제품 특징·사용법·주의사항·구매방법 질의응답
2. 기업 제공 자료 기반 **문서 검색(RAG)** 및 답변
3. 실제 사용한 근거 문서/FAQ 항목 표시
4. 대화 초기화 및 재질문
5. 자료에 없는 질문에 대한 답변 제한 및 상담 연결
6. PC·모바일 지원 챗봇 화면
7. 인터넷에서 접속 가능한 URL 배포
8. 웹서비스 개발팀 홈페이지에 삽입 가능한 형태
9. 대표·예외 질문 **20~30건** 평가, 분류·비율 산출, 개선 전후 비교
10. GitHub 소스코드, 실행법 README, 품질 평가 리포트, 발표자료

### 2.2 우선순위 규칙 [P]

- **P0:** 기업 필수 MVP 수행에 필요한 기능 또는 제출조건
- **P1:** 필수 구현을 돕는 편의·유지보수 기능. 일정에 따라 조정
- **P2:** 기업의 선택 도전과제 또는 팀 추가 제안

### 2.3 선택 기능 [E: 선택 / P: 구체화]

FAQ 바로가기·추천 질문, 질문 로그 화면, API 사용량·응답 시간·비용 측정, 답변 설정 2개의 동등 비교, 별도 관리자 통계, 사용자 만족도 입력 등은 **필수 완성 후 검토**한다. 특히 **카테고리·제품 선택 UI는 첫 질문의 필수 단계로 두지 않는다.**

### 2.4 범위 제외 [X]

AI 모델 자체 학습·파인튜닝, 실제 고객 데이터를 사용하는 운영, 상담원 배정·티켓 시스템, 상용 수준의 인증·보안 체계 구축. 단, API 키 비노출·최소한의 접근 제한·오류·개인정보 보호 등 MVP 기본 안전장치는 필요하다.

## 3. 사용자 흐름과 시나리오

### 3.1 기본 흐름 [T/E]

```text
고객이 챗봇 열기
  → 제품/카테고리 선택 없이 질문 입력
  → 관련 제품 자료와 FAQ 검색
  → 실제 답변 근거 확인
      ├─ 충분·일치: 답변 생성 + 근거 출처 표시
      ├─ 제품 구분 불가: 필요한 경우 짧은 추가 질문 [P]
      └─ 자료 부족/충돌/개별 상담: 확인 불가 안내 + 공식 상담 경로
  → 고객 재질문 또는 대화 초기화
```

### 3.2 대표 시나리오

| ID | 상황 | 기대 동작 |
|---|---|---|
| UC-01 | 고객이 제품 사용법 질문 | 관련 근거 검색 → 답변 및 출처 표시 |
| UC-02 | 고객이 제품명 없이 충전 질문 | 가능한 범위의 자료 검색 → 제품별 답이 다르면 추가 확인, 임의 제품 답변 금지 |
| UC-03 | 고객이 제품명을 명시 | 해당 제품 근거가 확인될 때 그 정보로 답변, 다른 제품 설명 혼합 방지 |
| UC-04 | 자료에 없는 정책·효능 문의 | 임의의 사실·정책 생성 없이 한계 안내 |
| UC-05 | 개인 주문·환불·AS 처리 요청 | 챗봇이 직접 처리했다고 주장하지 않고 공식 상담 경로 안내 |
| UC-06 | 고객이 대화 초기화 | 화면과 실제 대화 문맥에서 이전 대화가 새 질문에 적용되지 않도록 처리 |
| UC-07 | API·검색 시스템 장애 | 오류 안내 및 안전한 재시도/상담 안내 |

> 제품명·모델명이 여러 개 존재하는지와 제품별 다른 사용법은 **[O] 실제 제품 원본 확인 필요**. 위 UC-02/03은 혼동 방지를 위한 설계 기준이다.

## 4. 기능 요구사항 — 상세

각 기능의 **인수 기준(AC)**은 실제 테스트할 수 있는 조건으로 작성했다. 필수 기능이라도 구체적인 UI 문구, 수치 제한, 처리 방식은 팀 검토가 필요한 **[P] 후보**다.

### FR-001. 고객 자연어 질문 입력 [E/T] — P0

- **사전 조건:** 고객이 챗봇에 접속함.
- **입력:** 자유로운 자연어 질문.
- **처리:** 제품·카테고리 선택 없이 질문을 접수하고 백엔드 처리 흐름으로 전달한다.
- **출력:** 고객 질문이 화면에 표시되고 처리 상태를 알 수 있다.
- **예외:** 빈 입력, 전송 중 중복 클릭, 네트워크 오류, 과도하게 긴 입력.
- **AC:** (1) 첫 질문에 제품·카테고리 선택을 강요하지 않음 (2) 빈 질문 요청 방지 (3) 요청 실패가 사용자에게 표시됨 (4) 모바일·PC에서 입력 가능.
- **연관:** API-CHAT, UI-CHAT, TC-001/005.

### FR-002. FAQ·문서 근거 검색 [E] — P0

- **입력:** 자연어 질문 및 필요 시 현재 대화에서 확인된 제품 식별 정보.
- **처리:** 기업 제공 FAQ·설명서에서 질문에 관련된 근거를 검색한다. 원본 출처와 식별 가능해야 한다.
- **출력:** 검색 후보, 출처/원문 위치, 근거 적합 여부.
- **예외:** 검색 실패, 무관 문서, 미검증 자료, 모델 간 정보 충돌.
- **AC:** (1) 질문과 연결된 근거의 원본을 추적할 수 있음 (2) 미확인 답변을 공식 확정 정보처럼 취급하지 않음 (3) 자료가 없는 경우 충분한 근거가 있다고 반환하지 않음.
- **연관:** DATA-01~06, TC-002/003.

### FR-003. 근거 기반 답변 생성 [E] — P0

- **입력:** 사용자 질문과 검증된 검색 근거.
- **처리:** 검색 문서에 있는 정보만으로 설명하고 근거를 벗어난 제품 효과·정책을 만들지 않는다.
- **출력:** 고객에게 표시할 답변, 결과 상태.
- **예외:** 상충된 근거, 모호한 제품, 생성 실패.
- **AC:** (1) 답변의 사실 주장과 표시한 근거가 일치 (2) 미확인 사항을 확정 표현하지 않음 (3) 모델 오류 시 성공 답변으로 위장하지 않음.
- **연관:** API-CHAT, TC-002/006.

### FR-004. 답변 출처 표시 [E] — P0

- **입력:** 답변 생성에 사용한 원본의 식별자와 위치.
- **처리:** 실제 사용한 FAQ/문서명·원본 항목을 추적 가능하게 연결한다.
- **출력:** 답변 옆에 출처 또는 근거 정보 표시.
- **예외:** 출처 없음, 자료 접근 불가, 검색 후보만 있고 답변 근거로 사용하지 않은 경우.
- **AC:** (1) 존재하지 않는 출처를 표시하지 않음 (2) 답변과 무관한 검색 결과를 근거로 오표시하지 않음 (3) 평가자가 원문 대조 가능.
- **연관:** DATA-03/04, TC-002.

### FR-005. 답변 불가·상담 연결 [E] — P0

- **입력:** 근거 없음/불충분, 개별 주문·환불·AS 등의 요청, 안전·건강 관련 확인 불가.
- **처리:** 확답을 제한하고 기업이 확인한 상담 경로를 안내한다.
- **출력:** 답변 제한 문구와 이용 가능한 상담 경로.
- **예외:** 공식 상담 URL·채널 미제공.
- **AC:** (1) 자료 없는 질문에 가공한 사실·정책 미생성 (2) 상담 주소 미확인 시 임의 링크를 만들지 않음 (3) 안내 실패가 정상 답변으로 위장되지 않음.
- **연관:** API-CHAT/API-SUPPORT, TC-003/004.

### FR-006. 대화 재질문·초기화 [E] — P0

- **입력:** 후속 질문 또는 '초기화' 선택.
- **처리:** 후속 질문 흐름을 지원하고 초기화 후 이전 대화 내용/문맥이 재사용되지 않도록 한다.
- **출력:** 새 질문 답변 또는 초기화된 대화 화면.
- **예외:** 세션 유지 방식에 따라 서버 문맥이 남는 문제.
- **AC:** (1) 연속 질문 가능 (2) 초기화 후 이전 질문이 새 답변에 영향을 주지 않도록 테스트 (3) 재질문·초기화 UI 작동.
- **연관:** API-CHAT, API-SESSION(조건부), TC-007.

### FR-007. PC·모바일 고객 UI [E/T] — P0

- **입력:** 접속 기기 및 질문.
- **처리:** 자연어 질문 중심의 채팅 화면 제공, 모바일·PC 화면 대응.
- **출력:** 입력창, 대화 표시, 출처, 오류·상담 안내, 초기화 기능.
- **예외:** 작은 화면, 긴 답변, 긴 출처, 네트워크 장애.
- **AC:** (1) 첫 화면에서 직접 질문 가능 (2) 모바일에서 입력·전송·대화 스크롤 가능 (3) 필수 정보가 화면 밖에 가려지지 않음 (4) 관리자 화면 없이 고객용 흐름 완성.
- **연관:** UI-01~04, TC-008.

### FR-008. 배포·홈페이지 삽입 가능 형태 [E] — P0

- **입력:** 웹사이트 연동 조건 및 배포 환경.
- **처리:** 외부 접속 가능한 URL을 배포하고 홈페이지에 삽입할 수 있는 방식 및 설정을 제공한다.
- **출력:** 접속 주소, 삽입 안내, README.
- **예외:** iframe 제한(CSP/X-Frame-Options), 다른 도메인 API 호출 제한(CORS), 호스팅 정책, 비밀키 노출.
- **AC:** (1) 외부 기기 접속 확인 (2) 테스트 페이지에서 삽입 검증 또는 제약·대체안을 문서화 (3) 비밀키가 클라이언트 코드에 포함되지 않음.
- **연관:** DEP-01~03, TC-009.

### FR-009. 공식 FAQ·지식 데이터 반영 [E] — P0

- **입력:** 기업 제공 FAQ·제품 문서 및 변경 이력.
- **처리:** 자료별 원본을 보존하고 검색에 필요한 데이터로 변환. 원문 답변과 후보 답변의 검증 상태 구분.
- **출력:** 원본 추적 가능한 검색 인덱스와 처리 기록.
- **예외:** 문서 파싱 누락, 잘못된 Chunk 결합, 제품 혼동, 원문 손상.
- **AC:** (1) 원문으로 역추적 가능 (2) 원문 대비 핵심 조건·주의사항 누락 확인 (3) 미검증 후보를 자동으로 공식답변으로 승격하지 않음.
- **연관:** DATA-01~06, TC-010.

### FR-010. 답변 품질 평가 및 전후 비교 [E] — P0

- **입력:** 대표·고객문의·예외 등 평가 질문 20~30개, 정답 근거, 실행 결과.
- **처리:** 결과를 정답/부분 정답/오답/근거 없는 답변으로 분류하고 비율을 산출. 개선 전후 동일 평가세트로 비교한다.
- **출력:** 평가 기록, 집계, 오류 유형, 변경·재평가 결과.
- **예외:** 정답 근거 미확보, 평가 기준의 불일치, 질문 유출로 인한 평가 왜곡.
- **AC:** (1) 평가 질문과 기준 근거 식별 (2) 4개 판정 모두 적용 가능한 기준 보유 (3) 실제 평가 분모·개수·비율 표시 (4) 변경 전후 조건 기록.
- **연관:** EVAL-01~05, TC-011.

### FR-011. 코드 및 제출물 [E] — P0

- **입력:** 구현 소스·설정 예시·실행 절차·테스트·발표자료.
- **출력:** GitHub 코드 저장소, README, 평가 리포트, 배포 URL, 발표자료.
- **AC:** (1) README에 설치·환경변수 이름·실행법·한계 기재 (2) 실제 비밀키 미포함 (3) 배포 주소·평가 결과가 실재하는지 확인 (4) 제출 목록 대조.

### FR-012. FAQ 바로가기·추천 질문 [E: 선택] — P2

- 고객이 **선택할 의무 없이** 바로 질문할 수 있는 상태를 유지한 채, 자주 묻는 질문 링크를 선택적으로 보여줄 수 있다.
- **AC 후보:** 추천 항목이 없거나 눌리지 않아도 자연어 입력 기능은 정상 동작.

### FR-013. 질문 로그 및 사용량 지표 [E: 선택] — P2

- 선택 구현 시 개인 정보 최소화 및 관리자 접근 제한 필요.
- **AC 후보:** 실제 수집한 데이터와 집계값의 일치 확인. 구현되지 않으면 완료로 표시하지 않음.

### FR-014. 제품 식별·모호한 질문 대응 [P] — P1(필수 품질과 연관)

- 제품/카테고리 선택을 고객에게 강요하지 않는다.
- 검색 과정에서 문서에 실제 적힌 제품명·모델·공통 적용 범위를 활용하는 방안을 검토한다.
- 서로 다른 제품의 정보가 섞이면 제품을 물어보거나 확인 불가를 안내한다.
- **AC 후보:** 제품 구분이 필요한 질문에서 틀린 모델의 답변을 단정하지 않음.
- **미결:** 실제 제품군 목록, 자동 라우팅/메타데이터/하이브리드 검색 채택 여부.

### 5.1 분류 및 저장 형식

- 고객 화면에 제품·카테고리 선택을 요구하지 않는다. **내부에서 제품별 정보를 식별할 필요**와는 별개의 문제다.
- FAQ 8대 분류(제품 소개·기능 / 사용 방법 / 충전·배터리 / 착용·편의성 / 고장·문제 해결 / 안전·건강·효과 / 구매·배송·AS / 관리·보관)는 **기존 정리의 분류 체계**이다. 검색·표시에서 반드시 사용할지 여부는 별도 판단.
- JSON, JSONL, Markdown 및 저장 payload 형태는 **미확정**이다.
- 원문 21개 FAQ를 이용한 개인 실험을 먼저 진행할 수 있으나, 답변 원문 대조 및 고객 공개 승인 여부는 별도 확인이 필요하다.

### 5.2 개인별 실험과 제품 요구사항 분리

팀원은 공통 안전·출처 기준을 지키되 Chunking 방식, 크기, Overlap, 파싱 방법 등을 다르게 실험할 수 있다. 비교할 때는 가능한 한 **동일 원본·동일 평가 질문·동일 검색 조건**을 사용하고, 함께 변경한 설정을 반드시 기록한다. 결과가 좋다고 자동으로 팀 표준으로 승격하지 않는다.

## 8. 검증·인수 계획

### 8.1 시험 데이터 [E/P]

- **20~30개 평가 질문**: 대표 제품 질의, 동일 의미의 다른 표현, 모호한 질문, 근거 없는 질문, 관련 없는 질문, 상담 필요·주의사항 포함.
- 평가 질문마다 예상 근거 문서·질문 목적·판정 기준을 기록한다.
- 기업 제공 FAQ 및 실제 문서에서 확인되지 않은 제품 정보는 정답 근거로 삼지 않는다.

### 8.2 평가 판정 [E]

| 판정 | 판단 기준 초안 |
|---|---|
| 정답 | 질문에 필요한 사실을 확인된 근거와 일치하게 제공 |
| 부분 정답 | 핵심은 맞지만 필요한 내용 일부 누락 |
| 오답 | 근거와 모순되거나 제품을 잘못 식별 |
| 근거 없는 답변 | 문서에 없는 내용을 사실처럼 만들어 제공 |

동시에 여러 문제가 있다면 일관된 우선 판정 규칙을 합의해야 한다. **근거가 없는 질문에 적절히 답변을 제한한 사례는 실패로 자동 분류하지 않도록 별도 성공 여부를 기록**하는 것이 좋다.[P]

## 11. R01 → R02 개정 요약

1. **기업 필수·팀 합의·설계 후보·미결·범위 제외**를 분리했다.
2. 제품·카테고리 선택 없이 **직접 질문하는 팀 합의**를 반영했다.
3. 질문·검색·생성·출처·상담·대화·배포·평가별 **입력/출력/예외/인수 기준**을 보완했다.
4. 제품 구분이 모호한 경우 **잘못된 제품 설명을 단정하지 않는** 설계 기준을 추가했다.
5. **전용 Vector DB 사용 결정**은 유지하고, 특정 DB·JSON·Chunking 방식은 확정하지 않았다.
6. 개인별 Chunking 비교 실험을 정식 제품 요구와 구분했다.
7. 별도 관리자 화면을 MVP 필수에서 제외하고 선택 기능으로 유지했다.
8. API 계약, 시험 사례, 완료 증거, 주말 일정, 미결사항을 연결했다.

**원본 보호:** 본 문서는 기존 R01을 덮어쓰지 않는 **R02 개정 후보**이다. 팀 검토·승인 전까지 정본/구현 완료 자료로 표시하지 않는다.
