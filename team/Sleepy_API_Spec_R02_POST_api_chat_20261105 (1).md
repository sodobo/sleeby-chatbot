# Sleepy RAG AI 고객상담 챗봇 — API 명세서 R02

| 항목 | 내용 |
|---|---|
| 문서 ID | `SLEEPY-API-R02` |
| 작성 기준일 | 2026-11-05 (KST) |
| 상태 | **CANDIDATE — 팀 검토용 초안** |
| 서비스 | Sleepy RAG AI 고객상담 챗봇 |
| 대상 | 고객용 채팅 프론트엔드 ↔ FastAPI 백엔드 |
| 엔드포인트 | **`POST /api/chat` 한 개** |
| 별도 엔드포인트 | 이번 MVP 범위에 추가하지 않음 |
| 연계 문서 | Sleepy 요구사항 명세서 R02(초안) |

> **상태 구분:** 고객이 제품이나 FAQ 카테고리를 먼저 선택하지 않고 바로 질문하는 방식은 팀의 잠정 합의다. 전용 Vector DB 사용은 결정됐으나, 제품·임베딩 모델·Chunking·검색 알고리즘·데이터 포맷과 이 문서의 상세 API 필드는 미확정이다. 이 문서는 구현과 팀 논의를 위한 **제안 규격**이며 실제 구현·시험 결과가 아니다.

## 1. 목적 및 범위

사용자의 자연어 질문을 받아 관련 Sleepy 제품·FAQ 자료를 검색하고, 근거가 충분하면 답변 및 **실제 사용한 출처**를 반환한다. 근거가 불충분하거나 질문 대상 제품을 구별할 수 없으면 추측하지 않고 추가 확인 또는 고객지원 안내를 반환한다.

- 고객 화면은 **제품 선택·카테고리 선택 없이** 질문을 전송한다.
- 질문, 추가 질문, 답변, 출처, 답변 불가, 제품 확인 요청, 상담 안내는 **모두 동일한 API**로 처리한다.
- 대화 초기화는 우선 프론트엔드에서 처리한다. 서버 측 대화 저장 여부는 미정이다.
- FAQ 목록 조회·관리자 통계·별도 상담 API는 이 명세의 대상이 아니다.
- 토요일 Vercel 프로토타입은 실제 RAG 연동 전이라면 **목업 응답을 실제 AI 답변으로 표시하지 않는다.**

## 2. 통신 규격

| 항목 | 설계 후보 |
|---|---|
| Method | `POST` |
| Path | **`/api/chat`** |
| Content-Type | `application/json; charset=utf-8` |
| Accept | `application/json` |
| 통신 | 운영 배포 시 HTTPS |
| 인증 | 고객용 공개 API 전제 검토. 인증·요청 제한 방식은 미정 |
| 응답 방식 | 단일 JSON 응답(스트리밍은 이번 범위 밖) |
| Base URL | 배포 환경 확정 후 기재. 임의의 도메인 주소는 지정하지 않음 |

**중요:** URL은 `/api/chat`이다. 기존 초안의 `/api/v1/chat`은 이 후보 명세에서 사용하지 않는다. URL이 하나라는 뜻은 RAG 내부 동작이 하나라는 뜻은 아니다.

## 3. 요청(Request)

### 3.1 최소 요청 예시

```http
POST /api/chat
Content-Type: application/json
```

```json
{
  "message": "충전이 안 되는데 어떻게 해야 하나요?"
}
```

### 3.2 필드 정의

| 필드 | 타입 | 필수 | 설명 / 검증 기준 |
|---|---|---|---|
| `message` | `string` | **Y** | 공백만 입력된 질문은 거부. 최대 길이 제한은 팀 협의 후 확정 |
| `history` | `array` | N | 이전 대화 맥락을 전달하는 **선택적 설계 후보**. 미구현이면 보내지 않음 |

`history` 사용을 결정할 경우의 **예시**:

```json
{
  "message": "그럼 충전 시간은요?",
  "history": [
    {"role": "user", "content": "SLEEBY 충전 방법 알려줘"},
    {"role": "assistant", "content": "공식 자료를 확인해 충전 방법을 안내했습니다."}
  ]
}
```

- 위 `history`의 assistant 문장은 **규격 예시 문구**이며 실제 제품 안내 정보가 아니다.
- 서버 저장 방식(`session_id`)은 확정하지 않았다. 대화 문맥 구현 방식에 따라 `history`를 채택하거나 별도 세션 설계를 정해야 한다.
- 모델의 내부 시스템 지침, API 키, 고객 개인정보 등은 요청에 포함하지 않는다.

## 4. 공통 정상 응답(Response)

**HTTP 200**은 요청을 정상 처리했다는 뜻이다. **답변을 생성하지 못한 경우도** 예측 가능한 정상 처리라면 200과 상태값을 반환한다.

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `status` | `string` | **Y** | 아래 4개 처리 상태 중 하나 |
| `answer` | `string` | **Y** | 고객에게 표시할 안내 문구. 승인되지 않은 제품 사실을 만들지 않음 |
| `sources` | `array` | **Y** | 실제 답변에 사용한 근거. 없으면 `[]` |
| `needs_support` | `boolean` | **Y** | 상담 안내 필요 여부 |
| `support_url` | `string \| null` | **Y** | **공식 확인된** 고객지원 URL만 설정. 미확인 시 `null` |
| `follow_up_question` | `string \| null` | **Y** | 제품 구별 등 추가 정보가 필요하면 사용자에게 묻는 질문 |

### 4.1 `status` 값

| 상태 | 의미 | 프론트엔드 행동 |
|---|---|---|
| `answered` | 충분한 근거를 사용해 답변 생성 | 답변과 출처 표시 |
| `clarification_needed` | 제품·모델 또는 질문 의도가 불분명 | 확인 질문 표시 후 사용자의 새 질문 전송 |
| `insufficient_context` | 검색 근거가 부족하여 답변 제한 | 확인 불가 안내, 필요 시 상담 링크 |
| `support_required` | 개별 문의·공식 확인이 필요한 사안 | 상담 안내, 확인된 링크가 있을 때만 제공 |

### 4.2 출처 객체(`sources[]`)

| 필드 | 타입 | 설명 |
|---|---|---|
| `document_id` | `string` | 원본 문서 식별자 |
| `title` | `string` | 고객에게 노출 가능한 원본 문서명 또는 FAQ 제목 |
| `faq_id` | `string \| null` | FAQ일 경우 해당 식별자 |
| `location` | `string \| null` | 페이지·절·항목 등 원본 내 위치. 확인 불가 시 null |

- `sources`에는 **실제로 검색·검토하여 답변 근거로 사용한 자료만** 넣는다.
- 벡터 검색에서 상위에 나왔다는 이유만으로 출처를 자동 표시하지 않는다.
- 원문·FAQ 답변 승인과 공개 가능 여부는 별도 검증이 필요하다.
- 여러 제품 간 답변이 상충하면 한 제품의 정보를 다른 제품에 적용하지 않는다.

## 5. 시나리오별 응답 예시

> 아래 예시는 **API 구조 설명용 가상 데이터**이며 실제 Sleepy 제품 정책이나 검색 성능을 입증하지 않는다. 문서 ID·제목·답변은 테스트용 예시다.

### 5.1 근거 있는 답변 (`answered`)

```json
{
  "status": "answered",
  "answer": "확인된 제품 안내 자료에 따르면 해당 제품의 충전 방법은 안내서의 충전 항목을 참고해 주세요.",
  "sources": [
    {
      "document_id": "DOC-EXAMPLE-001",
      "title": "충전 안내서(가상 예시)",
      "faq_id": null,
      "location": "충전 방법"
    }
  ],
  "needs_support": false,
  "support_url": null,
  "follow_up_question": null
}
```

실제 구현 시 `answer`는 문서의 **구체적으로 확인된 사실**로 작성해야 한다. 위 문자열은 제품별 충전 방법을 설명하는 답변이 아니다.

### 5.2 질문 대상 확인 필요 (`clarification_needed`)

```json
{
  "status": "clarification_needed",
  "answer": "어떤 제품에 관한 문의인지 확인이 필요합니다.",
  "sources": [],
  "needs_support": false,
  "support_url": null,
  "follow_up_question": "사용 중인 제품명이나 모델명을 알려주시겠어요?"
}
```

고객에게 처음부터 제품을 **선택하도록 강제하지 않으며**, **질문만으로 안전하게 구별할 수 없을 때** 추가 질문한다.

### 5.3 검색 근거 부족 (`insufficient_context`)

```json
{
  "status": "insufficient_context",
  "answer": "현재 확인 가능한 자료에서는 해당 내용을 확인하지 못했습니다. 정확한 안내는 고객지원 채널로 문의해 주세요.",
  "sources": [],
  "needs_support": true,
  "support_url": null,
  "follow_up_question": null
}
```

### 5.4 개별 상담 필요 (`support_required`)

```json
{
  "status": "support_required",
  "answer": "교환·환불 등 개별 주문 정보 확인이 필요한 문의입니다. 공식 고객지원 채널로 문의해 주세요.",
  "sources": [],
  "needs_support": true,
  "support_url": null,
  "follow_up_question": null
}
```

기업 공식 상담 URL이 확인되면 `support_url`에 실제 URL을 설정한다. **임의 주소는 생성하지 않는다.**

## 6. 오류 응답 및 HTTP 상태

| HTTP | 예시 오류 코드 | 발생 조건 | 화면 처리 |
|---|---|---|---|
| `400` | `EMPTY_MESSAGE` | 질문 미입력·공백만 입력 | 질문 입력 안내 |
| `422` | `VALIDATION_ERROR` | JSON 형식 또는 필드 타입 검증 실패 | 잘못된 요청 안내 |
| `429` | `RATE_LIMITED` | 요청 제한 초과 | 잠시 후 재시도 안내 |
| `500` | `INTERNAL_ERROR` | 서버 내부 오류 | 일반 오류 안내 |
| `503` | `SERVICE_UNAVAILABLE` | GPT API·검색 서비스 등 필수 의존성 장애 | 서비스 이용 불가 안내 |

**오류 응답 예시**

```json
{
  "error": {
    "code": "EMPTY_MESSAGE",
    "message": "질문을 입력해 주세요."
  }
}
```

- 정상적인 **답변 불가(`insufficient_context`)는 HTTP 500 오류가 아니다.**
- 실제 FastAPI/Pydantic 기본 검증은 422를 반환할 수 있다. 빈 질문 400 처리 등은 명시적으로 구현해야 하며 **현재 확정 규약이 아니다.**
- 오류 응답에는 내부 예외 스택·API 키·프롬프트·고객 개인정보를 포함하지 않는다.

## 7. 내부 처리 계약 (별도 외부 API 없음)

1. **질문 수신:** 빈 질문과 입력 형식 검증.
2. **질문 이해·검색:** 임베딩 및 전용 Vector DB 검색. Semantic/Hybrid/Reranking 등은 개인별 실험 대상으로 유지.
3. **제품 적용 범위 확인:** 제품명이 있으면 해당 제품의 근거를 확인. 제품이 불명확하고 서로 다른 제품 정보가 충돌하면 `clarification_needed`.
4. **근거 검증:** 공식/미확인 자료를 구분하고 답변 가능한 근거인지 판단.
5. **응답 생성:** 충분한 근거가 있으면 GPT API로 답변 생성.
6. **출처 검증:** 생성된 답변이 사용 근거와 일치하는지 확인하고 `sources` 구성.
7. **답변 제한·상담:** 근거가 부족하거나 개별 대응이 필요한 경우 알맞은 `status` 반환.

**미확정:** Vector DB 제품, 임베딩 모델, 파싱·Chunking 방법, 저장 형식(JSON/JSONL 등), 검색 Top-K·임계값, LLM 프롬프트 및 재평가 기준. 팀원의 개별 실험 결과를 공통 API나 확정 구현 기술로 자동 승격하지 않는다.

## 8. 프론트엔드 연동 규칙

- 첫 화면에 채팅 입력창 표시. 제품·FAQ 카테고리 **선택 강제 없음**.
- 답변 생성 요청 중 중복 전송 방지 또는 요청 상태 표시.
- `answered`: 답변과 확인 가능한 출처만 표시.
- `clarification_needed`: 추가 질문 표시, 고객이 답하면 같은 `/api/chat` 재호출.
- `insufficient_context` / `support_required`: 정해진 안내 표시. 공식 링크가 없으면 링크를 임의 표시하지 않음.
- **대화 초기화:** 프론트엔드가 표시 중인 메시지 및 유지 중인 문맥을 초기화. 서버 저장이 확정되면 추가 설계 검토.
- 모바일·PC 반응형, 요청 실패 메시지, 재질문을 지원.
- 실제 백엔드 미연결 Vercel 프로토타입에서는 **목업/시연 응답임을 명시**.

## 9. 테스트 및 인수 기준 (후속 구현 시)

| 테스트 ID | 조건 | 기대 결과 |
|---|---|---|
| TC-01 | 제품 선택 없이 질문 전송 | `/api/chat` 요청 가능 |
| TC-02 | 공식 근거로 답변 가능한 질문 | `answered`, 답변·실제 근거 출처 반환 |
| TC-03 | 존재하지 않는 제품 특성 질문 | 추측 답변 없이 `insufficient_context` 또는 확인 요청 |
| TC-04 | 제품별 설명이 다르고 질문에 제품명 없음 | `clarification_needed` |
| TC-05 | 개별 환불·주문 문의 | `support_required` 및 공식 상담 안내 |
| TC-06 | 공백 입력 | 유효성 오류 반환 |
| TC-07 | 응답 데이터 타입 오류 | 검증 실패 처리 |
| TC-08 | 검색 시스템·GPT API 장애 | 안전한 오류 응답, 비밀정보 미노출 |
| TC-09 | 연속 질문 | 채택한 문맥 방식에 따라 동작 검증 |
| TC-10 | 화면 대화 초기화 | 이전 대화가 화면과 다음 요청 문맥에 남지 않음 |
| TC-11 | 모바일·PC | 주요 화면에서 질문·답변·출처 표시 가능 |
| TC-12 | 출처 없는 답변 | 출처를 허위 생성하지 않음 |

기업 과제의 20~30개 품질 평가 질문은 **별도 평가 데이터셋**으로 실행하고 정답·부분정답·오답·근거 없는 답변을 기록한다. 위 테스트 표는 실행 결과가 아니라 **계획**이다.

## 10. 현재 결정 상태 및 미결사항

| 내용 | 상태 |
|---|---|
| 고객이 화면에서 제품·카테고리 선택 없이 바로 질문 | 팀 잠정 합의 |
| 전용 Vector DB 사용 | 결정 |
| 외부 고객용 API를 `POST /api/chat` 하나로 설계 | 이번 명세 요청 반영. 팀 최종 승인 여부는 별도 확인 |
| 관리자 화면 | 이번 프로토타입 범위 제외 |
| 제품별 자동 식별, 검색·필터링 | 구현 방안 미확정 |
| DB 제품, 임베딩·Chunking·파싱·저장 형식 | 미정 / 개인별 비교 실험 대상 |
| `history` 사용 여부·문맥 보존 방식 | 미정 |
| 상담 링크·배포 도메인 | 공식 확인 필요 |
| 위 요청·응답 JSON 상세 필드 | **팀 검토용 제안**, 확정 아님 |
| API 실제 구현 및 테스트 | 미실행·미검증 |

## 11. 변경 이력

| 버전 | 변경 내용 | 상태 |
|---|---|---|
| R01 | 7개 고객·운영 API 후보로 구성 | 과거 초안. 원본 보존 |
| **R02** | 외부 API를 **`POST /api/chat` 한 개**로 축소; 제품 선택 없는 직접 질문; 출처·추가 확인·상담·오류·테스트 기준 통합 | **신규 CANDIDATE** |

**최종 상태:** 팀 검토용 초안 · 팀 승인 미확인 · 서버 구현/시험 미실행. 원본 요구사항 및 R01 API 명세서는 이 파일 생성만으로 수정되지 않는다.
